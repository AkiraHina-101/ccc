# API Index — `_clean/docs/` Entry Point

Purpose: this is the entry point for the whole AI-readable HyperMesh /
HyperView / HyperGraph / Python API reference under `_clean/docs/`. Its job
is to let an AI agent (or a human) pick the *right* file fast instead of
reading all ~21 files. Each entry below gives scope, product/layer, and an
overall confidence tier. Confidence tiers used across this folder (weakest
to strongest evidence): `UNVERIFIED/UNKNOWN` < `LOCAL-INSTALL` <
`RUNTIME-TESTED` / `OFFICIAL`. Most files mix tiers per-claim; the
tier listed per file below is the file's *dominant/overall* tier, not a
guarantee every line in it carries that tier.

For the full per-file official-vs-local coverage cross-check, see
`OFFICIAL_ALTAIR_2022_3_VERIFICATION.md` (grouped under Meta/Process below).

## Vocabulary — start here

These two files are the foundational "what entity types and attribute keys
exist" reference. Every other HyperMesh-layer file assumes you already know
these — read them first before anything else in the HyperMesh core group.

- **`HYPERMESH_ENTITY_TYPE_INDEX.md`** — Authoritative list of all 174
  HyperMesh entity type strings (157 named, 17 id-only), captured live via
  `hm_getentitytypes all` / `hm_getentitytypes named` against a real
  `hmbatch.exe -tcl` HyperMesh session. This is the correct
  vocabulary for the `<type>` argument in `hm_getvalue`, `*createmark`,
  `*setvalue`, etc. Per-type dataname enumeration is explicitly NOT covered
  here (see next file). **Tier: RUNTIME-TESTED (LOCAL-INSTALL).**

- **`HYPERMESH_DATANAME_INDEX.md`** — Per-entity-type index of valid
  attribute-key strings for `hm_getvalue <type> id=$id dataname=<KEY>`,
  generated by probing `hm_attributeindexmax`/`hm_attributeindexidentifier`/
  `hm_attributeindexvalue` live against the real test model
  (`01-Test_Model.hm`) plus fallback probes for well-known scalar keys not
  surfaced by the attribute index. Covers props/mats/elems fully, comps/
  nodes/subsystems via fallback, and 10 of 11 originally-zero-instance types
  via synthetic `*createentity` instances (clearly labeled SYNTHETIC);
  `connectors` remains unresolved (needs the separate `hm_ce_*` Connector
  API, out of scope for this file). Large, mostly auto-generated data-dump
  tables — treat as a lookup table, not reading material.
  **Tier: RUNTIME-TESTED (LOCAL-INSTALL), partially SYNTHETIC.**

## Composites (ply / laminate authoring)

- **`HYPERMESH_COMPOSITES_API_REF.md`** — Tcl automation for creating/editing
  composite `plies` and `laminates` entities (`*plycreate`, `*plyupdate`,
  `*laminatecreate`, `*laminateupdate`, plus a table of confirmed-existing
  but not-exercised commands like `*plydrape`, `*plyabsorb`,
  `*laminaterealize`). Explicitly does NOT duplicate PCOMP/PCOMPG/PCOMPLS/
  PCOMPP card fields — see `HYPERMESH_NASTRAN_CARD_FIELD_REF.md` for those.
  Confirmed this is a genuinely thin API surface: a handful of C-registered
  commands, with the rest of `hm/scripts/composites/`+`hyperlaminate/` being
  GUI dialog/tree-widget callback code around those same few commands (the
  `hyperlaminate/*.tbc` files turned out to be plain ASCII Tcl, not closed
  bytecode like HyperGraph's `.tbc` — but same GUI-callback content, no extra
  commands found there). Plain-stack ply+laminate create/link round-trip
  live-tested end-to-end; interface-laminate form and most secondary
  commands are source-read only.
  **Tier: RUNTIME-TESTED (core create/update pair) + LOCAL-INSTALL
  (interface-laminate form, secondary commands) + UNVERIFIED (several
  commands listed by name only, purpose inferred).**

## HyperView

- **`HYPERVIEW_API_REF.md`** — The classic HyperView "HVCmd" legacy Tcl
  dispatcher layer: 7 single-word commands (`dis`, `crs`, `gro`, `opt`,
  `rea`, `sty`, `ani`) covering displacement/contour, cross sections,
  groups, misc options, model/result loading, display style, animation.
  Also includes an appended "AdvancedTools Layer (advtools)" section (16
  callable `::post::advtools::vector::*`/`::post::advtools::matrix::*`
  utility procs, plus a flagged likely real bug in matrix `Inverse`).
  Presence of all 7 dispatcher commands confirmed live via `info commands`
  in a batch probe; internal subcommand behavior read from source only (no
  model/result was loaded in the probe). `gro`'s `prcShowGroup`/
  `prcHideGroup` flagged as dead/unreachable code (UNVERIFIED).
  **Tier: RUNTIME-TESTED (existence) + LOCAL-INSTALL (behavior);
  advtools sub-section LOCAL-INSTALL/UNVERIFIED.**

- **`HVTRANS_CONVERSION_WORKFLOW_REF.md`** — Practical workflow reference
  for using HvTrans (`hvtrans.exe`, `::hw::RunHVTrans`, `SaveConfig`/
  `LoadConfig`/`SetCompressionLevel`/`SetCompressionTolerance`/
  `SetCallback`/`ListItems`/`GetItemValue`) to filter/convert large Nastran
  BDF+OP2 pairs before HyperView mode-shape capture. Not a complete API
  reference — a targeted workflow note.
  **Tier: mixed OFFICIAL (Translators category) + LOCAL-INSTALL
  (exact command list, read from installed Tcl source); CLI behavior on the
  real 1.5GB/40-80GB files flagged RUNTIME-TEST-NEEDED.**

- **`OP2_BDF_MODESHAPE_CAPTURE_WORKFLOW.md`** — Proposed end-to-end
  operating strategy (not an API reference) for going from a large Nastran
  `.bdf`+`.op2` pair to still images/animated GIFs of mode shapes, built on
  top of the HvTrans and HyperView-capture references. Explicitly labeled a
  recommendation, not an Altair guarantee.
  **Tier: PROPOSED-WORKFLOW (own dedicated tier) + OFFICIAL (Batch
  Mode/HWI/HyperView view-class mechanisms) + LOCAL-INSTALL (exact
  HvTrans/AVI flow); full pipeline flagged RUNTIME-TEST-NEEDED end-to-end.**

## Python (native + MDI + Tcl-bridge)

- **`HYPERMESH_PYTHON_NATIVE_API_REF.md`** — The native `hw/python/hm/`
  package (`import hm`, `import hm.mdi`, `import hm.entities`), independent
  of the Tcl bridge. Exhaustive read of every source file in that package
  (confirmed via Glob). Not documented in Altair's public scripting
  help — appears to be internal MDI plumbing. Found 2 real source bugs
  (flagged, not fixed). Behavior implemented in compiled `hw.mdi.core`
  (.pyc) or C++ extension modules is inferred from call sites only, flagged
  RUNTIME-TEST-NEEDED.
  **Tier: LOCAL-INSTALL (source-read); no OFFICIAL basis.**

- **`HYPERMESH_PYTHON_MDI_API_REF.md`** — The Unified Desktop (`hwx`) MDI
  plugin layer at `hwx/plugins/mdi/` — a separate UI-integration layer (not
  domain entity semantics) that wires Client/ClientObject/Profile/Object
  into the `hwfwg` shell (Project Browser, Property Editor, ribbon, save/
  open). All 7 source files read fully; 6 classes, 54 methods/properties
  documented. Found 9 real bugs/inconsistencies (flagged, not fixed:
  unguarded cache lookup, asymmetric exception handling, dead icon-state
  branch, inconsistent None-guards, singular/plural attribute mismatch,
  unguarded IndexError, swapped tooltip text, disabled-but-implemented
  Smart Clipboard profile, inconsistent `Session()` construction patterns).
  **Tier: LOCAL-INSTALL (source-read); no OFFICIAL basis.**

- **`HYPERMESH_PYTHON_EMBEDDING_API_REF.md`** — Using Python inside
  HyperMesh/HyperWorks alongside the project's Tcl macro/table/entity
  APIs — embedded Python, the `Tclinter` Python-to-Tcl bridge, local Python
  paths/packages. Focuses on what's in the installed software, not
  newer HM Python APIs. Points to the two files below for detailed
  capture/view API and batch limits.
  **Tier: mixed OFFICIAL (underlying Tcl/HWI layer) +
  LOCAL-INSTALL (bridge/path details); active-interpreter behavior per
  launch mode flagged RUNTIME-TEST-NEEDED.**

- **`HYPERWORKS_PYTHON_VIEW_CAPTURE_API_REF.md`** — Controlling view
  orientation/fit/display-style and screenshot capture from Python in
  HyperMesh and HyperView/Post, via the `Tclinter.tcl.eval`/`.call`
  bridge or HWX `py:` profile commands (43 commands retrofitted this
  session).
  **Tier: mixed OFFICIAL (HWI handle syntax, `CaptureScreen`,
  `poI3DViewCtrl`, `hm_windowtofile`/`hm_windowtoclipboard`) +
  LOCAL-INSTALL (Tclinter bridge, AVI capture examples); direct

  RUNTIME-TEST-NEEDED.**

## Auto-expansion domains

- **`HYPERMESH_HYPERSTUDY_API_REF.md`** — The HyperMesh <-> HyperStudy
  integration bridge (`hm/scripts/HyperStudy/*.tcl`): a file/task bridge, not
  a live in-process API — HyperStudy launches one-shot `hw.exe`/
  `hmbatch.exe` batch processes per task (Import: interactive parameter-pick
  dialog writing a `.hstp`; Write: headless, reads a `.hstp` with concrete
  values and mutates the model via `*attributeupdatedouble`/`*loadsupdate`/
  etc. before a solver-deck export). Documents the real generic HyperMesh
  `parameter` entity mechanism (`*createentity parameter`, `*setvalue
  parameter ... valuedouble=`, `*setparameter`,
  `hm_isentitydatanameparameterized`) that HyperStudy design variables
  actually use, live-verified end-to-end linking a parameter to a real
  PSHELL property's thickness attribute on `01-Test_Model.hm`. Explicitly
  distinguishes this from the unrelated OptiStruct/RADIOSS
  `designvars`/`dvprels`/`dequations`/`optiresponses` structural-optimization
  entity types (already covered by `HYPERMESH_DATANAME_INDEX.md` Track 4) —
  do not conflate the two "design variable" systems.
  **Tier: mixed LOCAL-INSTALL (full source read of the Nastran-profile
  task scripts) + RUNTIME-TESTED (the parameter-creation/link/query chain and
  the `*hs*`/`*desvar*`/`*parameter*` command-existence survey).**

- **`HYPERMESH_MODELCHECK_API_REF.md`** — Altair's built-in ModelCheck
  rule-based model-QA framework: profile XML configs (e.g. `nastran.xml`,
  62 checks covering missing material, unused/empty entities, duplicate
  elements, ID-length, mass/thickness sanity checks) plus a real
  `hm_*modelcheck*`/`*modelcheck_*` Tcl command layer to load/run/read them
  headlessly. Full check-create -> run -> read-back cycle confirmed live
  end-to-end via `hmbatch.exe -tcl`, including the correct
  `modelcheckchecks` dataname set (`name`/`status`/`runstatus`/`level`/
  `checkentity`/`config`/`childids`/`failedids`) not resolvable from a
  SYNTHETIC instance alone (extends the Track 4 gap in
  `HYPERMESH_DATANAME_INDEX.md`). Also documents the separate, much thinner
  `ModelCheckerFramework`/`ModelCheckerTools` GUI-only element-quality-check
  tool (out of scope for detailed API documentation — flagged so it isn't
  confused with the main ModelCheck framework). Flags several checks
  (missing material, unused property/material, duplicate elements,
  components-share-property, thickness/density sanity) as directly
  overlapping this project's own hand-built QA ideas in `HANDOFF.md`.
  **Tier: RUNTIME-TESTED (LOCAL-INSTALL) for the command layer and
  check-entity dataname set; UNVERIFIED for exact `runstatus`/`level`/
  `checkentity` integer-code semantics (test model had zero failing
  checks, so pass/fail code meaning is inferred, not directly observed);
  corrections layer is LOCAL-INSTALL (source-read) — not live-applied,
  by design (model-mutating).**

- **`HYPERMESH_CONNECTORS_API_REF.md`** — the Connector Browser's real
  authoring API: `*CE_*`/`*AE_*` uppercase batch-macro mutation commands
  (create/realize/detail-set/export/organize connectors and attachments)
  plus the separate lowercase `hm_ce_*` read-only query family. Resolves
  the `connectors`-entity-creation gap `HYPERMESH_DATANAME_INDEX.md`
  flagged as unresolved — real path is `*CE_ConnectorCreateByMark`, not
  `*createentity`/`*createspotweld`; live-confirmed create -> query ->
  realize round trip (`hm_entitylist connectors`, `hm_ce_type`,
  `hm_ce_state`, `*CE_Realize`, element count increase). ~35 of 242+ real
  commands (132 `*CE_*` + 10 `*AE_*` + ~100 `hm_ce_*`) documented in
  depth; the rest named/existence-only, explicitly scoped down per the
  file's own honesty note.
  **Tier: RUNTIME-TESTED (create/realize/query round trip) +
  LOCAL-INSTALL (most signatures, source-read) + UNVERIFIED
  (commands with no call site and no live test, clearly labeled inline).**

## How to use this if you're an AI agent building automation code

1. **Read the vocabulary files first.** Start with
   `HYPERMESH_ENTITY_TYPE_INDEX.md` and `HYPERMESH_DATANAME_INDEX.md` so you
   have real entity-type strings and real dataname keys before writing any
   `hm_getvalue`/`*setvalue`/`*createmark` call. Every other HyperMesh-layer
   file assumes this vocabulary.
2. **Then read the relevant product-layer file(s)** from the groups above —
   don't read the whole folder. Pick by what you're touching: HyperMesh
   entity/GUI/render/batch/Nastran-cards, HyperView, HyperGraph, or Python
   (native/MDI/Tcl-bridge).
3. **Trust tiers, don't blend them:**
   - `OFFICIAL` and `RUNTIME-TESTED` content can be used directly —
     it was either confirmed by Altair's own help or actually
     executed and observed.
   - `LOCAL-INSTALL` content is probably correct (it was read from
     real installed source, not guessed) but is a sanity-check candidate if
     a live HyperMesh/HyperView session is available before you rely on it
     for something consequential (e.g. a bulk model mutation).
   - `UNVERIFIED` / `UNKNOWN` / `RUNTIME-TEST-NEEDED` content is exactly
     that — do not rely on it without live verification first. Several
     files call out specific UNVERIFIED items inline (e.g.
     `hm_entityinfo color`, `gro`'s `prcShowGroup`/`prcHideGroup`, HyperGraph
     live-probe inconclusiveness) — check those notes before using the
     surrounding command.
4. Check `OFFICIAL_ALTAIR_2022_3_VERIFICATION.md` if you need to know
   whether something is officially documented by Altair at all, independent
   of any single file's claim.
